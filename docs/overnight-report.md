# 사용감 개선 기록

브랜치 `overnight-improvements`. `main`에 병합하지 않았으므로 실제 사이트에는 아직 반영되지 않았다.
속도 수치는 로컬 dev 모드 기준이라 절대값보다 전후 비교로 본다.

## 1회차: 악보 목록

| 항목 | 전 | 후 |
|---|---|---|
| 체크박스 반응 | 약 175ms | 약 18ms |
| 처음 받는 썸네일 | 688개 전부 | 화면에 보이는 약 30개 |
| 모바일 가로 넘침 | 665px (화면 375px) | 없음 |
| 모바일 ⋮ 메뉴 | 가로 스크롤 끝에 숨음 | 바로 보임, 40px |
| 체크박스 누르는 영역 | 체크박스 크기 | 44×56px |

- 검색이 타이핑을 막지 않게 했다.
- 모바일에서는 Key와 BPM을 제목 아래에 표시한다.
- 목록의 Key 칸에 제목에서 읽은 Key도 표시한다.

## 2회차: 미리보기와 악보 페이지 용량

| 항목 | 전 | 후 |
|---|---|---|
| 미리보기를 열었을 때 | 약 2초 동안 빈 화면 | 썸네일 즉시 표시 후 원본으로 교체 |
| 다음 곡으로 넘길 때 | 빈 화면 | 썸네일 22ms, 원본 335ms |
| 본 곡을 다시 열 때 | 처음부터 다시 받음 | 210ms (브라우저 캐시 사용) |
| 여러 쪽 PDF | 모든 쪽을 그린 뒤 표시 | 첫 쪽부터 표시 |
| 악보 페이지 First Load JS | 380KB | 173KB |
| 콘티 편집 페이지 First Load JS | 201KB | 193KB |

- 업로드, 수정, 내보내기 코드는 쓸 때 불러온다. 첫 클릭 때 잠깐 기다릴 수 있다.
- 미리보기와 연주모드는 페이지를 연 뒤 미리 받아 둔다.

## 3회차: 콘티 편집 타이핑

| 항목 | 전 | 후 |
|---|---|---|
| 메모 한 글자 입력 | 약 82ms | 약 5ms |
| 라이브러리에서 곡 추가 | 전체 카드 재렌더 | 약 10ms |

- 원인은 dnd-kit 센서 옵션이었다. 렌더링마다 새 객체를 넘겨 688개 카드가 매번 다시 그려졌다.
- 화면 밖 라이브러리 카드는 그리기를 건너뛰게 했다 (`content-visibility`).
- 마우스 순서 변경(위, 아래), 라이브러리에서 끌어오기, 추가 버튼 상태를 다시 확인했다.

## 4회차: 페이지 이동

| 항목 | 전 | 후 |
|---|---|---|
| 악보 탭 첫 화면 | 515~843ms | 약 335ms (전체 행은 뒤이어 그림) |
| 새로고침 때 로그인·팀 조회 | 레이아웃과 페이지가 각각 조회 | 요청당 한 번 |

- 편집 화면의 라이브러리도 첫 30개를 먼저 그린다.
- 서버 위치는 문제없었다. Vercel은 서울(`icn1`)이고 DB 쿼리는 약 90ms다.
- 로그인하지 않은 요청이 401이나 로그인 화면으로 가는 것을 다시 확인했다.

## 5회차: 연주모드 조작

| 항목 | 전 | 후 |
|---|---|---|
| 곡을 처음 넘길 때 | 약 400ms 빈 화면 | 2~7ms |
| 연주모드 나가기 | Esc, 전체화면 해제만 | 닫기 버튼 추가 |
| 여러 쪽 PDF에서 방향키·스페이스 | 2쪽을 건너뛰고 다음 곡 | 쪽부터 넘기고 끝나면 다음 곡 |
| 넘기는 방법 | 스와이프, 방향키, 스페이스 | 화면 양쪽 30% 탭, 페달(PageUp/PageDown) 추가 |
| 모달 닫기 | 버튼만 | Esc로도 닫힘 (저장·다운로드 중 제외) |

- 숨긴 곡이 `display:none`이라 크기가 0이어서, 미리 그리기가 실제로는 동작하지 않고 있었다.
- 연주 중 화면이 꺼지지 않게 Wake Lock을 요청한다. 시험 브라우저가 권한을 거부해 실제 동작은 확인하지 못했다. 실제 태블릿에서 봐야 한다.
- 처음 한 번 "화면 양쪽 끝을 누르면 넘어갑니다"를 보여준다.
- 가운데 40%를 눌러도 넘어가지 않지만, 양쪽 끝은 실수로 닿으면 넘어간다. 연주 중 불편하면 끌 수 있게 바꿔야 한다.
